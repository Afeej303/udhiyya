## Concurrency & Stateless Multi-Worker Architecture

1. **Stateless Cryptographic Preview Tokens:**
   - Previews are serialized and signed as `<base64url(payload)>.<hmac_signature>`.
   - Contains: `programmeId`, `policy`, `proposedAllocations`, `unmatched`, `unfilledSlots`, `expiresAt`, `nonce`.
   - **Multi-Worker Shared:** Survives server restarts and functions identically across any number of load-balanced container replicas without requiring in-memory caches or external Redis infrastructure.
   - **Tamper-Proof:** Client cannot alter participant IDs or animal IDs without failing the HMAC verification.

2. **Atomic Row-Level Locking (`FOR UPDATE`):**
   - In `commit()`, allocations are executed inside `prisma.$transaction`.
   - The transaction locks target animal rows: `SELECT id FROM "Animal" WHERE id IN (...) FOR UPDATE`.
   - Live share counts are evaluated under the lock, strictly enforcing `liveCount + 1 <= 7`.
   - Concurrent commits targeting the same animals are serialized, completely eliminating race conditions and preventing overselling beyond 7 shares.

**Run:**
```bash

```

| Invariant / Test | Expected Result |
|---|---|
| Partially filled animals | Considers existing allocations; remaining slots = 7 - existing. Never exceeds 7 shares |
| No animal exceeds 7 shares | Even with surplus participants, each animal caps strictly at 7 shares |
| No participant duplicate | Unassigned participants matched at most once |
| `household_first` policy | Groups members of same household into the same animal before moving to next animal |
| Stateless HMAC-signed token | Server issues verifiable stateless token containing signed proposal |
| Forged previewToken rejection | Rejects unsigned, altered or mismatched tokens with `INVALID_TOKEN` (400) |
| Caller proposal tampering | Ignored! Server decodes verified token payload, ignoring client body |
| Expired preview rejection | Tokens older than TTL (10m) rejected with `PREVIEW_EXPIRED` |
| Replay rejection | Replaying an already-committed preview token returns 410 Gone (PREVIEW_ALREADY_COMMITTED) |
| Atomic Row Lock | Animal IDs locked via `FOR UPDATE` within transaction boundary |

## V2 – Manual UI Check (≤ 5 minutes, run by M1 or M2)

**Checklist file:** `docs/VERIFICATION/EF-02.md`

### Setup
1. Set `FEATURE_EF_02=on` in `.env`.
2. Ensure backend is running and seeded with ≥ 1 programme, ≥ 7 approved participants, ≥ 1 animal (can be partially allocated).
3. Navigate to the **Allocations page** (slot `smart-allocation-slot` mounted by M1).

### Steps

| Step | Action | Expected result |
|---|---|---|
| 1 | Open Allocations page with flag on | `SmartAllocationPanel` renders with policy selector and **Run Smart Allocation** button (`data-testid="ef02-smart-allocation-btn"`) |
| 2 | Select "Household grouping first" policy and click **Run Smart Allocation** | Loading state shown (`data-testid="ef02-loading"`) |
| 3 | Inspect preview table | Preview table appears (`data-testid="ef02-preview-table"`). Household members are assigned to the same animal. No animal has > 7 total shares |
| 4 | Click **Confirm & Commit** | Committing indicator shown (`data-testid="ef02-committing"`), then success message (`data-testid="ef02-success"`) with count of committed allocations |
| 5 | Verify in DB / UI | Allocated participants now show as allocated in the main Allocations table |
| 6 | Set `FEATURE_EF_02=off`, reload page | Smart allocation slot disappears cleanly; rest of page functions normally |

### Pass criteria
- All 6 steps produce expected results
- Zero console errors
- MVP manual allocation continues to work regardless of flag state
